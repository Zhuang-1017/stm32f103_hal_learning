# 自定义通信协议（帧头 + 长度 + CRC16）· 面试一页纸

> 对应工程 `[19-11]自定义通信协议`｜STM32F103C8T6 @72 MHz｜USART1 115200 8N1
> 2026-11-24 整理。标「待实测」的项，面试时不要说得像已经量过。

## 30 秒开场

串口只给你字节流，没有边界、没有完整性校验。我在 USART 中断上叠了一层自定义帧：`AA 55` 定位帧头，`LEN` 定长度，`CRC16` 校验内容。解析用逐字节状态机，不依赖任何超时判断，所以粘包和半包天然成立。协议部分 250 行 C，整个工程 Code 6.9 KB，编译 0 Error 0 Warning。

## 一、帧结构

```
AA 55 │ LEN │ CMD │ DATA[LEN] │ CRC_L CRC_H
帧头     长度   命令    数据段        校验
```

- 整帧 = 6 + LEN；LEN ≤ 32；LEN = 0 时是最短的 6 字节纯命令帧
- CRC 覆盖 `LEN + CMD + DATA`，**不含两个帧头**；**低字节先发**（Modbus 惯例）
- CRC16/MODBUS：多项式 `0xA001`、初值 `0xFFFF`、无输出反转；`"123456789"` → `0x4B37`

| 字段 | 解决什么 | 为什么是它 |
| --- | --- | --- |
| `AA 55` | 从哪开始 | 单字节误同步概率 1/256，双字节 1/65536 |
| `LEN` | 到哪结束 | 长度是**内容**，与字节何时到达无关 |
| `CRC16` | 有没有坏 | 单比特 / 双比特 / 奇数位 / ≤16 bit 突发错 100% 检出 |

## 二、解析：7 态状态机

`HEAD1 → HEAD2 → LEN → CMD → DATA×(LEN) → CRC_L → CRC_H → 出帧`

```c
int8_t Proto_Parse(uint8_t byte, ProtoFrame_t *out);
/*  0 未成帧   1 成帧   -1 校验错   -2 长度非法  */
```

三个非显然的设计决定：

1. **`ST_HEAD2` 里再来一个 `0xAA` 不动作**，留在原状态 —— `AA AA 55 …` 这类重叠帧头也能同步；若回 `HEAD1` 会被自己的帧头带偏。
2. **`ST_LEN` 里 `LEN > 32` 立即 Reset 返回 -2**，不按非法长度收数据 —— `s_raw` 只有 34 字节，按 40 收会越界写。
3. **`ST_CRC_H` 里不论对错都 Reset** —— 对了要接下一帧（粘包），错了要重新找同步点。

## 三、三个真踩过的坑（面试最值钱的部分）

1. **`Transmit_IT` 后紧跟阻塞发送，一个字节都发不出去**：`_IT` 一返回 `gState` 就是 `BUSY_TX`，阻塞版第一句 `if (gState == READY)` 不成立，整串返回 `HAL_BUSY`。
2. **靠 IDLE 判帧**：`HAL_UARTEx_ReceiveToIdle_DMA` 同时开了半传输中断，64 字节帧收到第 32 字节就以 HT 事件回调一次，帧被切成两段；帧内停顿超过 1 个字符时间也会被切。**IDLE 是物理现象，不是数据内容。**
3. **把长度字段直接当索引用**：`&RxBuff[3]` 越界写正好命中 `uwTickFreq`（0x20000004），`uwTick` 被加错值，所有 `HAL_Delay` 快 88 倍 —— 现象是"程序整体跑飞"，根因离现场很远。

## 四、追问速答

| 追问 | 一句话 |
| --- | --- |
| 数据段里出现 `AA 55` 会不会误判？ | 不会。进 DATA 态后只按 LEN 计数，不再比对帧头；帧头匹配只发生在帧边界 |
| 为什么会粘包 / 半包，怎么处理？ | 不需要额外代码：状态存 static，出帧回 HEAD1。粘包 = 紧跟的 `AA 55` 自动成新帧头；半包 = 状态跨时间保留 |
| 校验错了为什么不回 NACK？ | 坏帧静默丢，重传交给应用层超时。回 NACK 也保证不了对端收到，反而多一次失败机会 |
| 为什么不用求和或奇偶校验？ | 求和看不出顺序（AB 与 BA 同值）；奇偶只覆盖奇数个比特翻转，双比特错完全看不见 |
| 帧头为什么用两个字节？ | 一字节误同步 1/256，两字节 1/65536；且数据段里出现 `AA` 不会被误当帧头 |
| 吞吐和开销？ | 32 字节数据 → 38 字节帧。115200 下每字节 86.8 µs，单帧约 3.3 ms，协议开销 6/38 ≈ 16% |
| 解析放在中断里安全吗？ | 前提是开销可控：逐位 CRC 约 0.9 µs/字节（**待 DWT 实测**），38 字节约 30 µs，小于一个字符时间 86.8 µs。LEN 放大到几百字节就必须搬到主循环 |
| 和 Modbus RTU 什么关系？ | 帧尾 CRC 参数完全一致（`0xA001` / `0xFFFF` / 低字节先发）。区别：Modbus 靠 3.5 字符静默判帧，我用长度字段，所以不怕分包和帧内停顿 |

## 五、收尾

它和 Modbus RTU 同源，但我把"靠时间判边界"换成了"靠内容判边界"。只改了这一处，粘包、半包、帧内停顿就全部自动成立。

错误分三类计数（CRC 错 / 长度错 / 主循环来不及处理丢帧），分开统计才能判断是线路噪声、上位机发错，还是 MCU 处理不及。
